### 0.1 Blind labelling (commitment)
Silver labelling of Test-A (labelled), Test-B and unseen-filer filings is done **blind to all model and baseline outputs (4B, 2B, B0, B1) on those filings**: no such output exists when labelling starts, because
the runbook labels all three splits first and runs models afterwards. This is enforced in code, not only by procedure: every labelling command and pipeline function (`pass-a`, `label-select`, `label-export`,
`label-compare`, `label-final`) calls `tt/labels/blind.py`, which **refuses any path inside `runs/` or with a `runs` directory in it** (read or write); labelling scratch lives under `data/labels/work/<split>/`; a test
(`tests/test_blind.py`) checks that `tt/labels/` does not import the agent, evaluation, baseline or Ollama code. The guard's SHA-256 is in the freeze record.
Limits, stated plainly: the labelling rules (`docs/LABELING_RULES.md`) were written on dev, in the same project and by the same assistant that saw the dev model results, so the labeller is not ignorant of how the models behave on dev. Blindness is to model and baseline outputs on the test filings only. The guard stops the labelling code reading `runs/`; it cannot stop a person or a model from being told a score in conversation, so the runbook forbids showing any score before all three label sets are hashed.

### 0.2 Label error (lower bound) and how every metric must be worded
Every metric in this document and in every result table, figure caption and sentence is stated **"against silver labels (AI-made, not human-verified)"**, followed by this label-error statement:
> Label error is unknown and not zero. A lower bound from the dev labelling: Pass A and Pass B disagreed on 113 compared items, so at least one of them was wrong on each of those items; Pass C ruled that Pass A's label was wrong on at least 83 of the 113 (77 sided with B, 6 corrected both) and right on 14, and 16 items stayed CONTESTED (excluded from scoring, counted). The final silver labels are Pass A plus those corrections, so errors that A, B and C share, and Pass C's own mistakes, are invisible to this process; no human checked any label. A measured model error is therefore error against silver labels: it can be too high (the silver label is wrong and the model is right) or too low (the model repeats the labellers' family mistake).
The same statistics (A-vs-B disagreements, Pass C outcomes, contested counts) are recomputed and reported for every test split.

### 0.3 Pass C is blind to which pass made which answer
For the test splits Pass C sees the two candidate answers as **version X and version Y in a seeded random order** (`tt/labels/protocol.py`, per-item coin flip from seed 0 and the item id) and is never told which pass produced which; even the "only in A / only in B" wording is rewritten to "only in X / only in Y". The X/Y-to-A/B mapping is stored only on the master items list (`items.json` in the comparison directory), never in a batch directory the subagent reads; decisions are X, Y, NEITHER or CONTESTED, and an answer of A or B is rejected as missing. `label-final` reports Pass C's agreement with Pass A and with Pass B **separately** (counts, rate over all compared items and over decided items, Wilson 95%) and how often it picked X vs Y, which shows any position preference. The updated `docs/PASS_C_PROMPT.txt` is hashed in the freeze record, and the freeze refuses a prompt that names pass A or B. Disclosure: the **dev** Pass C saw "version A / version B" (A was the draft that became the labels); its 77 B vs 14 A split on dev could partly reflect position or labelling effects and is not corrected.

### 3.1 Primary endpoint (H1, adopted by the owner) and its pass/fail rule
**Claim:** on the Test-A labelled set, the event claims the agent accepts (no verifier failed and run 2 agrees) have lower error than all event claims of the single pass (B2), and the agent does not get there by abstaining on almost everything.
**Metric:** error = share of event claims that are wrong against silver labels (AI-made, not human-verified); an event claim is right if a silver event of the same type has an overlapping date at the coarser granularity (`reports/phase_3.md`; an unparseable date is wrong; contested silver events are dropped). Delta = error(all B2 event claims) minus error(accepted agent event claims), paired, filer-cluster bootstrap (2,000 resamples, seed 0, percentile 95%). Coverage = accepted event claims / all event claims.
Random abstention at equal coverage has expected Delta 0, so a Delta lower bound above 0 shows the verifiers select errors, not just fewer claims.
**PASS if and only if all three hold:** (i) Delta >= 0.05; (ii) the 95% interval of Delta has its lower bound above 0; (iii) coverage >= 0.40. **FAIL otherwise**, including when there are no accepted claims. There is no third outcome and no "approaching significance".
Dev reference (in-sample, not evidence): Delta 0.100 (0.035 to 0.172), coverage 50.9%.
Limits of this endpoint, so the owner can reject it: (a) the comparator is the same model without the verifiers, so a pass shows the abstention filter removes errors, **not that the agent beats the rule baseline B1** (that is H5, secondary); (b) accepted claims are a subset of the B2 claims, so Delta > 0 is partly mechanical whenever the filter has any signal; (c) event correctness depends on the silver event typing, which is the weakest part of the labels (event A-vs-B agreement 68.7%). If the owner prefers a different primary, it must be a claim type that is not NR detection (section 3.3) and be fixed in `config/thresholds.json` before the freeze.

### 3.1b Which run
**H1, H2 and H5 use run 1 (temperature 0, seed 0): every claim that is scored comes from run 1.** Run 2 (temperature 0.5, seed 1) is a stability check only and its own claims are never scored; run-2 stability (how often run 2 reproduces run 1) is exploratory. One thing has to be said plainly: the agent's acceptance rule (and so H1's accepted set and H2's) includes "run 2 agrees" as a filter, exactly as in the dev design, so H1 and H2 use run 2 as a filter on run-1 claims. H5 does not use run 2 at all (B1 and B2 only). If the owner wants H1 independent of run 2, the acceptance rule (verifiers only) and the thresholds must be changed before the freeze; that is a different, weaker agent (dev: see `reports/phase_4.md`, "verifiers only").

### 3.3 What "cause error" measures (stated exactly)
- **Scored now: NR-or-not detection only.** Per filing, the prediction is the boolean `cause_reported`; it is correct iff it equals `silver cause.status == SUPPORTED` (`tt/eval/phase3.py`). A silver cause of NOT_REPORTED or INSUFFICIENT both count as "not reported" (dev: 70 SUPPORTED, 25 NOT_REPORTED, 5 INSUFFICIENT).
- **Not scored: the cause itself.** The silver C layer holds a status and a verbatim quote of the stated cause, but the model's output schema (`tt/agent/schemas.py`) has no cause text, so the quoted cause cannot be compared with anything. No claim about the correctness of any model's cause or mechanism is made anywhere. Reports say "NR detection", never "cause accuracy" (the dev-bench printout and `devscore.py` still use the key `cause_accuracy`; code is frozen, the report wording is not).
- **Same metric for the baselines.** B0 always answers the dev-majority value (`cause_reported = True`, from the dev silver labels, never from the split scored): its error is the share of test filings whose silver cause is not SUPPORTED (dev 0.300, 0.210 to 0.390). B1 answers `cause_reported = False` iff the cause text is empty or one of NR / N/R / N/A / NA / not reported / not available (dev 0.050, 0.010 to 0.100). B2 4B v2 on dev: 0.050 (0.010 to 0.099); the agent after the V4/V4r rules: 0.011 among accepted.
- **The agent's number is partly the verifier code.** V4 forces an NR cause to stay NR and V4r forces a stated cause to be reported unless the text says undetermined, so the agent's accepted-claim error here mostly measures those rules, which are close to B1's rule. B1 and the agent are expected to be close.
- **Consequence:** this is an NR-detection metric, so **it cannot be the primary endpoint** and `scripts/freeze.py` refuses if it is chosen. It is secondary (H2).

## 4. Analysis plan
Claim types: supplier claims (S2-type companies), event claims (all six types; the headline five-type F1 also reported), `cause_reported` (NR detection only, 3.3). Correctness rules are those in `reports/phase_3.md`.
Excluded and counted: contested labels, unlabelled companies (named in the text, no silver claim), unreadable filings. Curves: risk-coverage with deterministic score (0 if a verifier failed, else 1 + 2 x run-2 agreement + B1 agreement); ties are included fractionally. No model confidence is ever used.
Intervals: filer-cluster bootstrap, 2,000 resamples, seed 0, percentile 95%. Event matching: equal type and date-span overlap at the coarser granularity; fuzzy dates scored separately.

## 5. One-shot rule, negative-result commitment and reporting
- Model outputs for each split are produced once (run 1, run 2). No rerun, prompt, rule, threshold, metric, model, subset or label change after the first Test-A score is seen. Any deviation is written in `reports/deviations.md` with the reason, and the unmodified results are still reported.
- **Negative-result commitment.** Whatever the outcome, the results are reported with the same prominence and in full: if the primary endpoint FAILS, the first sentence of every report and write-up says "the primary endpoint was not met" with the numbers; the primary endpoint is not replaced, redefined or demoted after the fact; no secondary or exploratory result is promoted to stand in for it; if B1 or B0 match or beat the agent, that is stated in the same place as the agent's result; null and negative results go in the same tables as positive ones, including Test-B and unseen-filer; results are published even if unfavourable.
- Nothing is described as human-verified. Suppliers are "named in the filing as component manufacturer", never "responsible" or "caused".
